# ADR 0050 — The web UI ports onto Tailwind 4 in place, with a DOM-factory component kit instead of React

## Context

The page is a preact/htm and vanilla-JS app: 237 KB of hand-written CSS across app.css and views.css, a subsetted PatternFly v6 sheet for the frame chrome, and a design-token suite (ui/app/design-tokens.test.mjs) that pins radii, type steps, spacing and lamp values. The objective is to port all of it onto Tailwind 4 and shadcn. shadcn/ui ships as React source over Radix, generated by a CLI that assumes React, TypeScript and a bundler; this page has none of those. The webui WASM guest @embedFile's each shipped file at comptime and clanker serve runs no build step, so anything the browser downloads must exist in the tree.

seriously considered, and why the status quo (or the obvious alternative)

the constraint still holds without reading the whole codebase.

## Decision

Tailwind 4 via @tailwindcss/cli, compiled from ui/app/tailwind.src.css into a committed ui/app/tailwind.css by bun run css:build. The page loads it render-blocking after app.css, which makes it the layer that supersedes the cabinet rules as each view moves over. The @theme block holds no values: every entry is a var() reference to a token app.css already declares, so the seven themes and the dark query keep working and no theme key collides with the token it reads (a self-referential --radius-sm computes to nothing). The radius scale is the cabinet's (rounded-plate, rounded-plate-lg, rounded-capsule), and Tailwind's own rounded-sm/md/lg are cleared so a pasted shadcn snippet cannot silently round a plate into a SaaS card. Preflight is deliberately not imported yet: it resets margins, headings and controls, and app.css still owns those declarations; the one rule the utility layer needs from it (a border style) is inlined. shadcn's component source is re-cut rather than re-hosted: ui/app/core/kit.js builds DOM nodes through the existing tag factory, with shadcn's variant vocabulary expressed in cabinet utility names, because adding React, Radix, TypeScript and a bundler to a Zig-embedded static bundle is not a migration. The port is per file, and ui/app/tailwind.test.mjs carries the ledger: files whose cabinet rules are deleted are added to its migrated list, and the suite fails when a class in one of them has no rule in any shipped sheet (a utility written and never rebuilt), when padding or gap leaves the cabinet space scale, or when an arbitrary value bypasses the tokens.

## Consequences

Editing a class in ui/app or ui/plugins now requires bun run css:build, or the element silently styles nothing; tailwind.test.mjs fails instead, which is the guard, and every migrated file must keep resolving. The compiled sheet is a committed build product with its own weight budget, in the first-paint accounting and with its own asset cache kind in webui_assets.zig. The port deletes app.css, views.css and the PatternFly sheet only as views move over, so ordering matters: utilities win on equal specificity by being later, and preflight stays out until the last cabinet rule is gone. The kit only gains a component when a caller exists. Bundled CSS is not the only path: a view that never uses a utility costs nothing in the sheet, because Tailwind emits only the classes the sources name.

What this forecloses: the cabinet's styles stop being readable in one place. A class's appearance is now split between the utility string at its call site, the @theme mapping, and whatever app.css has not been moved yet, so a reader of a ported view must open tailwind.src.css as well. Reversing means porting every utility back into CSS, because no sheet holds the declaration. It also fixes the component vocabulary early: shadcn snippets copied in later arrive with React imports and rounded-md, and both have to be re-cut on arrival rather than dropped in.
