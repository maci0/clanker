# PRD — TTSR (Time-traveling stream rules)

## Status

Draft. No source files yet. Feature lives in `src/agent/loop.zig` (the streaming
path) and a new `src/agent/ttsr.zig` for the rule engine. Config lives in
`config.toml` under a `[ttsr]` section.

## Problem

The agent loop (`src/agent/loop.zig`) streams LLM output token-by-token and
passes the full completion to tools after the stream ends. There is no way to
inspect the partial stream as it arrives and intervene before the model finishes.
This matters when the model is about to do something wrong that a simple pattern
could detect early: it costs the full completion's tokens, and the correction
(if any) comes in the next turn, burning another full context's worth of
re-reasoning.

omp's TTSR (time-traveling stream rules) aborts the stream the moment a regex
fires, injects a rule into the system context, and retries from the same point,
so zero tokens are spent on the rule until a match happens. The rule survives
context compaction, so it keeps applying. Clanker has no equivalent: once a
stream starts, it runs to completion regardless of what comes out.

## Goals

1. A stream-intercept layer in the agent loop that applies ordered regex rules to
   the partial token buffer as bytes arrive and can abort an in-flight stream.
2. On match: the stream is torn down, the rule's injection text is appended to
   the system message, and the turn retries from the top of the think-act-observe
   cycle with the same user message.
3. Rules survive compaction: they live in the system context, not in conversation
   history that `maybeCompactMessages` can trim.
4. Rules are declarative: defined in `config.toml` under `[ttsr.rules]`, each
   with a `pattern`, an `inject` string, and an optional `max_fires` count
   (default 1). Note: the tree has no in-process regex engine today.
   `search_code` shells out to the `rg` binary (`tools/zig/search_code.zig`),
   and per-chunk streaming match cannot spawn a subprocess per chunk, so what
   engine backs `pattern` is an open question (see below).
5. Rule firings are logged to `state/ttsr.jsonl` with the matched token offset
   and the rule name, so they are auditable after a run.
6. A `ck_ttsr` host function lets WASM tools register ephemeral rules for the
   duration of one tool call, without touching `config.toml`.

## Non-goals

- Not a general output filter. Rules only abort-and-retry; they do not rewrite
  or suppress model output in place. Post-processing belongs to transforms
  (the existing `after`/`before` chain).
- Not real-time per-token semantic analysis. Patterns are plain regex against
  byte buffers, not embeddings or classifier calls. Expensive semantic checks
  belong in the advisor (PRD 0015), not here.
- Not a firewall for harmful content. Rules are developer-defined, not a content
  policy layer. Misuse of `max_fires = 0` (which would loop forever) is refused
  at load time, not a safety mechanism.
- Not retrying with a different model. The retry uses the same provider and model.
  Provider fallback is a separate concern.
- Not a post-turn critic. TTSR fires during a stream and aborts it; the advisor
  (PRD 0015) fires after a completed turn and only annotates the next one.
  Different interception points, deliberately.

## Design

**Rule schema (config.toml).**

```toml
[[ttsr.rules]]
name    = "no-rm-rf"
pattern = "rm -rf /"
inject  = "Never emit destructive shell commands without a dry-run flag."
max_fires = 3

[[ttsr.rules]]
name    = "no-force-push"
pattern = "git push.*--force"
inject  = "Prefer --force-with-lease; state why a force push is necessary."
```

Rules are applied in declaration order. `max_fires` limits how many times a
single rule may fire across the whole session (not per turn). At the limit, the
rule is silently disabled for the rest of the session and a warning is written to
the log.

**Stream interception.** The streaming path in `Agent.run` feeds tokens through
`client.chatStream`'s `on_token` hook. TTSR wraps this hook with a
`StreamGuard` (new type in `src/agent/ttsr.zig`) that:

1. Appends each chunk to a ring buffer (configurable via `ttsr.buffer_bytes`,
   default 4096).
2. After each append, runs the compiled regex set against the tail of the buffer.
3. On the first match, signals the stream to abort (sets the existing
   `stop_flag`, which `chatStream` already checks per chunk).
4. Records the match to `state/ttsr.jsonl`.
5. Returns the matched rule to the caller.

The ring buffer keeps only the tail so long runs don't accumulate. The regex
compilation happens at startup (or on first use), not per token.

**Retry mechanics.** When `StreamGuard` returns a matched rule, `Agent.run`:

1. Discards the partial assistant message from `session.messages` (it was not
   added to history yet, since history is only appended after a complete turn).
2. Appends the rule's `inject` text to the system message as an injected block
   tagged with `[ttsr:<name>]`.
3. Re-enters the turn loop from the top. The user message is unchanged; the
   injected rule is now visible.

The system message injection is append-only per rule name; a rule that fires
twice does not duplicate its block.

**Compaction survival.** `maybeCompactMessages` trims `session.messages` (the
conversation history), not the system prompt. Injected rule blocks live in the
system prompt, so they survive compaction without any special handling.

**`ck_ttsr` host function.** Signature:

```zig
fn ckTtsr(ptr: u32, len: u32) void
```

The guest writes a JSON payload:

```json
{"name": "my-rule", "pattern": "FIXME:", "inject": "Resolve all FIXMEs before continuing.", "max_fires": 1}
```

The host registers the rule for the current tool call's duration and removes it
on return. Ephemeral rules do not persist to `state/ttsr.jsonl` unless they
fire.

**`ck_stats` integration.** The existing stats pipeline records TTSR fire counts
per session alongside token counts, so `clanker stats` shows rule firings and
`GET /api/stats` exposes them.

## Failure modes

| Condition | Behaviour |
|---|---|
| Regex compilation fails at startup | Fatal: clanker refuses to start; logs the offending pattern and rule name |
| Stream aborts but the LLM endpoint returns an error on the teardown | The partial message is discarded; the retry proceeds as normal; the abort error is logged at debug level |
| Rule fires, retry fires the same rule again immediately | Counted against `max_fires`; at the limit the rule is disabled for the session; if every rule is disabled and the same pattern keeps appearing, the turn proceeds to completion (no infinite loop) |
| `ck_ttsr` called outside an active stream (e.g. from a non-streaming tool call) | Rule is registered but will never fire; logged as a no-op at debug level |
| `ttsr.buffer_bytes` too small to catch a multi-token pattern | Pattern simply does not match; no error. Document minimum buffer sizing in the manifest |

## Acceptance criteria

- [ ] `ttsr.rules` parsed from `config.toml`; invalid regex causes a startup
      error with the rule name and pattern in the message.
- [ ] `StreamGuard` intercepts an in-flight stream, fires a matching rule, and
      the turn retries with the injection visible in the system prompt.
- [ ] A rule that fires during a retried turn increments the fire counter; at
      `max_fires` the rule is disabled and the turn proceeds without aborting.
- [ ] Injected rule blocks survive a `maybeCompactMessages` call (verify by
      asserting the system prompt before and after compaction).
- [ ] `ck_ttsr` registers an ephemeral rule; a stream matching it during the
      tool call fires and retries; after the call returns, the rule is gone.
- [ ] `state/ttsr.jsonl` contains one entry per firing with rule name, turn
      index, and matched byte offset.
- [ ] `clanker stats` includes a `ttsr_fires` column; `GET /api/stats` exposes
      the same count.
- [ ] Unit tests in `src/agent/ttsr.zig` cover: regex match on a partial buffer,
      ring-buffer tail behavior, `max_fires` enforcement, and ephemeral rule
      cleanup.

## Open questions / future work

- **The regex engine is the feature's real cost.** Clanker has no in-process
  regex engine; `search_code` gets one by shelling out to `rg`, which does not
  work per chunk. The options: vendor a regex engine (largest new dependency in
  the tree), write a small subset matcher (cheap but limits `pattern`
  expressiveness and needs careful spec), or restrict patterns to
  literal/substring match (trivially streamable, but the examples above like
  `git push.*--force` stop working). Each tradeoff changes what rules users can
  write; this must be settled before implementation starts.
- **`ck_ttsr` needs an ADR.** Adding a host function grows the guest ABI, and
  ADR 0006 treats ABI growth as an ADR-level decision; an ADR is needed before
  `ck_ttsr` is added.
- **Retry budget.** Should there be a per-turn cap on TTSR retries independent
  of `max_fires`? An adversarial model could cycle through rules indefinitely if
  many rules share similar patterns.
- **Rule ordering on multiple matches.** Currently the first match in declaration
  order wins. Whether the highest-priority match (by a separate `priority` field)
  should win instead is unresolved.
- **Streaming vs. non-streaming providers.** Some provider configs disable
  streaming (`stream: false`). TTSR has no effect in that mode; should it warn or
  refuse to register rules when streaming is off?
- **Rule sharing across sessions.** `state/ttsr.jsonl` accumulates across
  sessions. Whether a rule's `max_fires` counter resets per-session or is
  lifetime-global is not decided; current spec is lifetime-global.
