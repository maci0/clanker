# PRD — DAP (Debug Adapter Protocol)

## Status

In progress. `tools/zig/debug.zig`, `tools/manifests/debug.tool.json`,
`src/debug/dap.zig`, `ck_debug`, and `[debug]` config are in. Gated by
`debug.enabled = false`. Adapters live in the 0016 session registry.
Host tests drive framing plus a stdio fake adapter (launch, breakpoints,
continue, stack, variables, evaluate, disconnect). A live `lldb-dap` /
`debugpy` / `dlv` launch is not required for the unit tests.

## Problem

When a tool or program misbehaves, the agent's only introspection path is to add
print statements, re-run, and read the output. There is no way for the agent to
attach a debugger, set a breakpoint, step through code, or inspect a call stack.
This makes debugging multi-threaded or crash-reproducing scenarios impractical:
the agent must instrument the code and re-run repeatedly instead of stopping at
the crash site.

The Debug Adapter Protocol (DAP) is a language-agnostic JSON-RPC protocol for
driving debuggers. `lldb-dap`, `dlv` (Go), `debugpy` (Python), `gdb-dap`, and
`node --inspect` all speak it. omp's DAP integration exposes 28 operations and 14
bundled adapters. A clanker equivalent lets the agent use any locally installed
DAP adapter without clanker knowing the language.

## Goals

1. A `debug` WASM tool that accepts a `op` field selecting one of the core DAP
   operations and delegates to a host-managed adapter process.
2. The host spawns and owns the adapter through the shared session-subprocess
   registry from PRD 0016 (not `ck_exec`: that is the guest's one-shot exec path
   and holds no process handle across tool calls), communicates over stdio using
   DAP's length-prefixed JSON-RPC framing, and tracks the adapter process across
   calls in the same session.
3. Supported operations (14): `launch`, `attach`, `set_breakpoints`, `continue`,
   `step_in`, `step_out`, `next`, `pause`, `stack_trace`, `scopes`, `variables`,
   `evaluate`, `disconnect`, and `terminate`.
4. Adapter type must be specified explicitly per call via `adapter` in v1 (no
   file-extension auto-detection). Config's `debug.adapters` table supplies the
   command lines. At minimum document and support: `lldb-dap` (native/C),
   `debugpy` (Python), and `dlv` (Go).
5. Gated by `debug.enabled = true` in `config.toml` (default false). The tool
   manifest sets `"confirm": true` (the manifest schema has no `dangerous` key;
   per-call confirmation plus the config gate is the existing mechanism).
6. Adapter state (process handle, active session) persists within a clanker
   session and is cleaned up on session end via the 0016 registry.

## Non-goals

- Not a GUI debugger. Output is structured JSON; the model reads variables and
  stack frames as text. There is no TUI or web UI view for breakpoints.
- Not implementing DAP from scratch. The host is a thin framing layer over stdio;
  it reads and writes JSON-RPC as bytes and lets the adapter handle all
  language-specific logic.
- Not supporting all 28+ DAP operations in the first version. The 14 listed in
  Goals cover the core debug loop (including `terminate`). Exotic operations
  (data breakpoints, exception filters, memory read/write) are future work.
- Not network-based attachment in the first version. The adapter is always
  spawned as a subprocess over stdio. TCP and Unix socket attachment are future
  work.
- Not a multi-session debugger. One active adapter per clanker session. Starting
  a second `launch` tears down the first.
- Not adapter auto-detection in v1. Callers pass `adapter` explicitly.

## Design

**Config.**

```toml
[debug]
enabled = true

[debug.adapters.lldb]
command = ["lldb-dap"]

[debug.adapters.python]
command = ["python3", "-m", "debugpy.adapter"]

[debug.adapters.go]
command = ["dlv", "dap"]
```

Each adapter entry names the command to spawn. Arguments are fixed per adapter
type (the adapter handles the rest via DAP initialize). Missing `adapter` on a
call is a tool error naming the configured adapter keys.

**Tool input schema (examples).**

```json
{"op": "launch", "adapter": "lldb", "program": "./myapp", "args": ["--flag"]}
{"op": "set_breakpoints", "source": "src/main.c", "lines": [42, 87]}
{"op": "set_breakpoints", "source": "src/main.c", "lines": [42], "condition": "x > 0", "hitCondition": "3"}
{"op": "continue"}
{"op": "stack_trace"}
{"op": "variables", "variables_reference": 3}
{"op": "evaluate", "expression": "x + 1", "frame_id": 0}
{"op": "disconnect"}
{"op": "terminate"}
```

**Conditional breakpoints (decided: pass-through).** DAP `setBreakpoints`
supports `condition` and `hitCondition`. The tool accepts these fields and
forwards them to the adapter unchanged. Document them in the tool schema /
manifest so the model knows they exist; no extra host validation beyond type
checks.

**DAP framing.** DAP uses HTTP-like headers over a byte stream:
`Content-Length: N\r\n\r\n{JSON}`. The host reads and writes this framing.
The host assigns monotonically increasing request `seq` numbers and tracks
pending requests by `seq` to match responses. Events (stopped, output, thread)
from the adapter are buffered and returned in the next tool call's response as
an `events` array.

**Adapter lifecycle.** On `launch` or `attach`:
1. If an adapter process is already running, send `disconnect` and wait for it
   to exit (timeout: `debug.disconnect_timeout_ms`, default 3000).
2. Spawn the configured adapter command via the PRD 0016 session-subprocess
   registry with a pipe pair for stdio. `ck_exec` cannot do this: it is the
   guest-to-host one-shot exec path (allowlist-gated, no long-lived handles
   across tool calls), while the adapter must outlive many tool calls.
3. Send DAP `initialize` with `clientID = "clanker"`.
4. Send `launch` or `attach` with the caller's arguments.
5. Wait for the `initialized` event.
6. Apply any pending breakpoints if `set_breakpoints` was called before `launch`.

On `disconnect` or `terminate`: send the appropriate DAP request and kill the
process after the timeout. Both ops are first-class in v1.

**Event buffering.** The adapter sends events asynchronously (e.g., `stopped`,
`output`, `exited`). The host reads them in a background thread and appends them
to an event queue. Each tool call response includes any queued events since the
last call, allowing the model to observe program state changes without polling.

**`stack_trace` and `variables` output.** These return structured DAP responses
translated to a flatter JSON representation:

```json
{
  "frames": [
    {"id": 0, "name": "main", "source": "src/main.c", "line": 42},
    {"id": 1, "name": "startup", "source": "libc.c", "line": 100}
  ]
}
```

Variables are similarly flattened. The raw DAP `variablesReference` is preserved
so the model can make follow-up `variables` calls for nested objects.

**`evaluate` scoping.** The `evaluate` operation sends a DAP `evaluate` request
in the `repl` context at the given `frame_id`. The result is the adapter's
`result` string and `type` field, returned as-is.

**Session cleanup.** When the clanker session ends, the 0016 registry sends
`disconnect` then SIGTERM after the timeout to any running adapter and removes
its pid. This PRD does not invent a second lifecycle manager.

**Dependencies.**

- **Hard:** PRD 0016 session-subprocess registry (register, session-end
  SIGTERM, keyed by session+kind). DAP does not ship until that registry exists.
- Config `[debug]` / `[debug.adapters.*]` parsing.
- WASM tool + manifest with `confirm: true` and `debug.enabled = false` default.
- Local DAP adapter binaries on PATH (`lldb-dap`, `debugpy`, `dlv`); absence is
  a runtime error on `launch`, not a build dependency.

**Implementation.**

1. **Wait on 0016 registry** (or land registry as a shared prerequisite PR if
   DAP work starts first, still owned by the 0016 contract).
2. **DAP framing** in `src/debug/dap.zig`: Content-Length read/write, `seq`
   tracking, event queue.
3. **Tool ops**: implement the 14 operations; require explicit `adapter`;
   pass through `condition` / `hitCondition` on `set_breakpoints`.
4. **Lifecycle**: register adapter processes with the shared registry; tear down
   on `disconnect` / `terminate` / session end / second `launch`.
5. **Config + gate**: `debug.enabled = false` default; disabled error path.
6. **Tests**: framing, seq matching, event buffering, lifecycle state machine,
   missing-adapter error.
7. **Deferred:** TCP/Unix attach; `threads` / per-thread `stackTrace`; proactive
   `/api/run` stopped events; adapter auto-detection.

## Known issues

- **Live adapter coverage is a fake stdio DAP server**, not `lldb-dap` /
  `debugpy` / `dlv`. Those binaries are optional; `launch` against a
  missing configured command is a runtime error. Re-confirmed 2026-08-23: a
  live attempt against Apple's `lldb-dap` never got an answer to `launch`,
  but plain `lldb -b -o run` hangs at `run` on the same machine, so that run
  says nothing about the client either way. The in-tree fakes are real
  `python3` processes over real pipes, which is what the two ordering fixes
  below are pinned against.
- **(Fixed) `launch` waited for an `initialized` event `initialize` had
  already queued.** DAP lets the adapter emit `initialized` any time after it
  receives `initialize`, and `initialize`'s `waitResponse` files every event
  it reads ahead of the response into `self.events`. `Session.launch`
  (src/debug/dap.zig) only inspected frames it read itself, so `saw_init`
  stayed false, its loop condition stayed true after the response arrived,
  and `readFrame` blocked on an adapter with nothing left to say — the whole
  launch rides `runBounded`, so a correct adapter was SIGTERMed and the tool
  returned `LaunchTimeout`. `launch` now runs the same pre-scan `waitEvent`
  two functions up already did. Both in-tree fakes send `initialized` after
  the launch request, the one ordering that worked, which is why the suite
  was green; `early_init_adapter_src` covers the other.
  [Record](../reports/bugs/2026-08-23-dap-launch-misses-a-queued-initialized-event.md).
- **(Fixed) `waitEvent` filed every frame as an event, so `attach` could lose
  its own response.** `waitEvent` appended each frame it read to
  `self.events` regardless of type, where `waitResponse` beside it queues
  only `type:event` frames. `attach()` waits for `initialized` and then for
  its response, so an adapter answering `attach` first had that response
  eaten: `waitResponse` could never match it, `attach` fell back to the
  literal `{"ok":true}`, and `writeEvents` spliced a `"type":"response"`
  object into the tool's `events` array as if it were an adapter event.
  `waitEvent` now goes through `noteFrame`, which parks a response for the
  `waitResponse` that wants it (`Session.responses`, capped at
  `max_parked_responses`) instead of misfiling or dropping it.
  [Record](../reports/bugs/2026-08-23-dap-waitevent-files-responses-as-events.md).
- **A run whose `debug` launch times out leaks a hash-map allocation.**
  Observed 2026-08-23 while checking the two fixes above against a real
  adapter: the run answers normally and then exits with a `DebugAllocator`
  leak report whose trace bottoms out in `std.hash_map.putContext`. The same
  run shape with no tools exits clean. Not traced to a file; the expiry path
  in `runBounded` and the `Registry` row teardown
  (`src/agent/subprocess.zig`) are the first places to look.
  [Record](../reports/bugs/2026-08-23-debug-tool-run-leaks-on-adapter-timeout.md).
- **(Fixed) Event buffering used to be drain-on-next-read**, and worse than
  the entry claimed: `drainAvailable` decoded only bytes a previous blocking
  read happened to over-read, so a `stopped` event sitting unread in the OS
  pipe was invisible until the next request's response wait swallowed it —
  `continue` to a breakpoint essentially never reported its own `stopped`,
  which surfaced attached to whatever tool call came next. Two changes, still
  no background thread: `Session.fillAvailable` (src/debug/dap.zig) pulls
  whatever the adapter has already written without blocking (poll(2) with a
  zero timeout via `Registry.stdoutReadable`, src/agent/subprocess.zig), so
  every drain sees arrived events; and resuming ops (`continue`, `step_*`,
  `next`, `pause`) wait up to `HandleOpts.stop_wait_ms` (default 1000, 0
  disables) for a stop-shaped event (`stopped`/`terminated`/`exited`) after
  their response, so the event lands on the call that caused it. Unlike the
  `request_timeout_ms` bound, an expired stop wait is not an error and never
  touches the adapter: a debuggee legitimately still running returns
  eventless and the late event is drained by the next call. Pinned by the
  delayed-stop adapter tests in src/debug/dap.zig.
- **(Fixed) `disconnect_timeout_ms` used to be stored but never honored.**
  `Session.disconnect` now waits up to `debug.disconnect_timeout_ms` for the
  adapter to exit on its own after the disconnect response
  (`Registry.terminateWithin`, `src/agent/subprocess.zig`) and SIGTERMs it
  only when that window lapses.
- **(Fixed) `launch_timeout_ms` used to be stored but never bound a launch.**
  `launchBounded` (src/debug/dap.zig) now runs the whole launch handshake
  (initialize + launch/attach) on an `io.concurrent` worker bounded by
  `debug.launch_timeout_ms`; on expiry the adapter is SIGTERMed (SIGKILL
  after a 2s grace) and reaped, and the tool returns a timeout error. The
  `HandleOpts` timeout copies are wired: `handle()` is the one writer of
  the `Session` timeout fields. `launch_timeout_ms = 0` disables the
  bound. Resolved in
  [the launch-timeout bug report](../reports/bugs/2026-08-21-dap-launch-timeout-never-bounds-launch.md).
- **(Fixed) Post-launch ops used to block unbounded on a silent adapter.**
  The bounded runner is generalized (`OpSpec` + `runBounded`): every
  post-launch request (`continue`, `stackTrace`, `variables`, ...) runs
  under `debug.request_timeout_ms` (default 15000, 0 disables), with the
  same kill-and-reap expiry as launch. Resolved in
  [the post-launch bug report](../reports/bugs/2026-08-22-dap-post-launch-ops-block-unbounded.md).

## Failure modes

| Condition | Behaviour |
|---|---|
| `debug.enabled = false` (default) | Tool returns a "disabled" error; no adapter spawned |
| `adapter` omitted or unknown | Tool returns a clear error listing configured adapter names |
| Adapter binary not found on PATH | `launch` returns a clear error with the expected command; no process is started |
| Adapter crashes immediately after spawn | Tool returns stderr content; state is cleared; next `launch` starts fresh |
| `launch` timeout (adapter does not send `initialized` within `debug.launch_timeout_ms`) | Process is killed; tool returns a timeout error |
| Post-launch request timeout (no response within `debug.request_timeout_ms`) | Process is killed and reaped; tool returns a timeout error (`disconnect`/`terminate` return ok with a note — teardown got its outcome) |
| DAP response `seq` mismatch | Logged and skipped; the tool returns the next valid response in sequence |
| `evaluate` expression causes adapter crash | Adapter restarts on next call (same as process crash path) |
| `set_breakpoints` called before `launch` | Breakpoints are queued and applied after the next successful `initialized` event |
| `disconnect` / `terminate` while no adapter is running | No-op; returns `{"ok": true}` |

## Acceptance criteria

- [x] `debug.enabled = false` (default): tool registered but returns a disabled
      error; no adapter process spawned.
- [x] `launch` requires an explicit `adapter` matching `debug.adapters`; omission
      or unknown name is an error.
- [x] `launch` with a valid adapter (configured command, or the in-tree fake
      adapter in tests) spawns the process, sends `initialize` + `launch`, and
      waits for `initialized`. Live `lldb-dap` is optional at runtime.
- [x] `set_breakpoints` applied after `launch` results in the adapter receiving a
      `setBreakpoints` DAP request with the correct source and lines; `condition`
      and `hitCondition` are forwarded when present.
- [x] `continue` sends a DAP `continue` request; the `stopped` event from the
      adapter is queued and returned on a tool response (`events`).
- [x] `stack_trace` returns a flattened `frames` array with at least the top
      frame's name and source location.
- [x] `variables` for a valid `variables_reference` returns a flat list of name,
      value, and type.
- [x] `evaluate` returns the expression result string from the adapter.
- [x] `disconnect` and `terminate` each send the corresponding DAP request and
      kill the process.
- [x] Session cleanup on session end uses the 0016 registry (disconnect then
      SIGTERM) for any running adapter.
- [x] A second `launch` tears down the first adapter before starting the new one.
- [x] Unit tests cover: DAP framing (length-prefix read/write), event buffering,
      request `seq` tracking, adapter lifecycle, explicit-adapter requirement.

## Open questions / future work

- **TCP/Unix socket attachment.** Future work; would replace stdio with a
  network connection.
- **Multi-thread visibility.** DAP `threads` and per-thread `stackTrace` remain
  future ops (useful for Go goroutines and Python asyncio).
- **Breakpoint hit notification.** Proactive `/api/run` `\x01` events for
  stopped state remain future work; v1 still buffers events onto the next tool
  response.
- **Adapter auto-detection.** Inferring adapter from program extension remains
  future work after v1.
